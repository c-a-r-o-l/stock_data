PART 1: CORE PROJECT ARCHITECTURE
================================================================================

PROJECT NAME: Market State Foundation Model (Stock GPT / MarketBERT)

GOAL: Build a system that encodes 60-252 days of market data into dense
embeddings, stores them in a Vector DB for similarity search, and uses XGBoost
to predict the probability of top decile future returns.

THREE-LAYER ARCHITECTURE:
- Level 1: Event Engine - Discretizes continuous data into tokens (later
  revised to use continuous embeddings instead)
- Level 2: Vector Similarity - Uses Faiss/ChromaDB to find Top 50 most similar
  historical cases
- Level 3: Gradient Boosting - XGBoost predicts P(6M Return > 50%)

FINAL ARCHITECTURE DECISION:
- Use Transformer Encoder (NOT GPT) - because we need representation for
  retrieval, not text generation
- Use Continuous Embeddings (NOT discretization/tokenization) - preserves
  numeric precision and smooth transitions
- Window size: 252 trading days (1 year) - captures ~4 quarterly updates
- Output: 768-dim embedding representing complete market state
- Two parallel paths: Faiss for interpretability (similar cases) + XGBoost
  for prediction (calibrated probability)

================================================================================
PART 2: KEY ARCHITECTURAL DECISIONS & RATIONALE
================================================================================

1. WHY TRANSFORMER ENCODER OVER OTHER METHODS?
   - Raw XGBoost: Loses time order completely; treats days as independent
   - LSTM: Forgets long-range patterns; cannot compare Day 1 and Day 60
   - Transformer: Bidirectional attention, no forgetting, learns cross-day
     relationships, parallel training
   - Positional encoding preserves time order

2. WHY CONTINUOUS EMBEDDINGS OVER DISCRETE TOKENS?
   - Preserves exact numeric values (95.4 vs 95.5)
   - Handles smooth transitions (no hard thresholds)
   - No arbitrary discretization boundaries
   - Better for financial data (numbers, not words)
   - Implementation: Linear Projection Layer (num_factors → 768)

3. WHY 252 DAYS WINDOW SIZE?
   - Quarterly data needs at least 2-3 updates in the window
   - 252 days = 4 quarterly updates (enough to see trends)
   - 60 days = only 1 quarterly update (too short)
   - Captures seasonal patterns and annual cycles

4. WHY BOTH FAISS AND XGBOOST?
   - Faiss: Interpretability (show similar cases, gain PM trust)
   - XGBoost: Accuracy (calibrated probability, uses all data)
   - They are PARALLEL paths, NOT a pipeline
   - Do NOT train XGBoost on Faiss results (overfitting on 50 samples)
   - Train XGBoost on ALL historical embeddings

5. WHY NO PRE-SOLVING CORRELATIONS?
   - Traditional ML (XGBoost): Correlations = problem (multicollinearity)
   - Transformer: Correlations = information (context)
   - Self-Attention handles correlated features dynamically
   - The correlation itself becomes a signal (degree of divergence)
   - Only drop features that are mathematically identical

6. DATA ALIGNMENT PRINCIPLE
   - Every day must have the same number of columns
   - Forward-fill slower frequencies to daily:
     - Weekly data: same value for 5 days
     - Monthly data: same value for 21 days
     - Quarterly data: same value for ~63 days
   - Macro data aligned to RELEASE DATE, NOT period end
   - Prevents look-ahead bias
   - Each economic release is a separate dataset; merge by release date

7. FEATURE ENGINEERING PRINCIPLES (Refined Through Debate):
   - Give raw ingredients, let model learn recipes (no pre-digested signals)
   - Do NOT provide binary crossover signals (SMA_20 crossed SMA_200)
   - Provide raw SMA_20 and SMA_200; Transformer learns the gap dynamically
   - Do NOT provide TTM (2*STD - 1.5*ATR); model learns better relationship
   - Keep Trigger (trend acceleration) but drop MACD_DIFF if redundant
   - Keep Fit (linear regression) because Fit ≈ SMA_020 signals big moves
   - Keep Fit_SPY, Trigger_SPY, Itrend_SPY for market context
   - Keep PV_BULL_* structural features (main force step logic)
   - Drop BIAS_Diff (complex conditional noise; redundant with CLOSE+SMA)
   - Drop Push_Diff (MACD-based rule; redundant with MACD_DIFF+Trigger)
   - Drop MACD_L (only needed for short side)
   - Drop oSlowK, oSlowD (redundant with RSI_03)

8. NORMALIZATION STRATEGY (Per Feature Type):
   - Raw Prices (OPEN, HIGH, LOW, CLOSE, SPY_*): Time-series Z-score
   - Volume, ATR, Counts: Robust Z-score (Median + MAD)
   - PFE, RSI, MACD: Raw values (no normalization)
   - Trend_PV: Raw integer (ordered discrete levels)
   - PV_BULL_START/STOP/H: Relative to CLOSE: (X - CLOSE) / CLOSE

PART 4: UNDERSTANDING THE ALPHA (EXCESS RETURNS)
================================================================================

ALPHA SOURCES IN THIS SYSTEM:

1. MICROSTRUCTURE ALPHA (Most Important):
   - Trend_PV captures "main force's step-by-step pushing" logic
   - Market often treats "main force" as simple big orders
   - This system quantifies the complete "attack → consolidate → attack again"
     cycle
   - Result: Hold strong stocks, avoid being shaken out

2. ASYMMETRIC ALPHA (Trend Exhaustion & Acceleration):
   - Trigger and Itrend capture trend acceleration/deceleration
   - Close > Trigger > Itrend confirms trend continuation (~100% reliability)
   - MACD_C > MACD_H with both rising = "overbought expansion" (bullish)
   - Result: Enter trends early, exit before price drops

3. REGIME-DEPENDENT ALPHA:
   - Traditional models use fixed weights across market regimes
   - This model uses macro context (SP_Above_200, VIX structure, Fosback)
   - Learns: "PV_BULL signal works in high breadth, low VIX environments;
     defensive factors work in crises"
   - Result: Model adapts to market conditions automatically

4. DATA ALPHA (Feature Engineering):
   - Features are not raw data (OHLCV) but structured insights
   - PFE (trend efficiency), PV_BULL_STEP (step duration), Fosback (fragility)
   - Reduces Transformer's learning burden
   - Result: First layer sees "trend quality" instead of learning it over 10
     layers

ALPHA EQUATION:
Alpha = (Main Force Attack Structure × Trend Acceleration) + (Overbought
Momentum Expansion × Market Breadth Filter) - (Noise in Panic Environments)

PART 6: PHILOSOPHICAL PRINCIPLES (Refined Through Debate)
================================================================================

1. GIVE RAW INGREDIENTS, LET MODEL LEARN RECIPES:
   - Do NOT pre-digest data into binary signals (crossovers)
   - Provide continuous time series and let Transformer discover patterns
   - Pre-digested signals introduce noise and threshold bias

2. TRUST THE BLACK BOX:
   - Transformer's Self-Attention handles correlations dynamically
   - Do NOT pre-solve correlations; they are information (context)
   - The degree of correlation between features becomes a signal itself
   - Only drop features that are mathematically identical

3. NO DATA LEAKAGE:
   - Macro data aligned to RELEASE DATE, not period end
   - Encoder only processes Days 1-252 (past window)
   - Never sees Day 253 or future returns
   - Train/Validation/Test: 1990-2018 / 2019-2021 / 2022-2024 (chronological)

4. NO DISCRETIZATION:
   - Financial data is numeric, not categorical
   - Preserve exact values and smooth transitions
   - Linear Projection Layer: num_factors → 768

5. FEATURE ENGINEERING PRINCIPLES:
   - No redundant features (remove highly correlated duplicates)
   - No pre-digested trading rules (remove conditional noise)
   - Preserve raw data and let Transformer learn relationships
   - Keep structural features encoding market microstructure
   - Keep market context features (SPY counterparts)
   - Normalize appropriately per feature type

6. WHY FORWARD-FILLING IS CORRECT:
   - Carries LAST KNOWN value forward until new data arrives
   - Uses only PAST data to fill future days
   - Exactly how a real-time system works
   - Does NOT introduce bias

7. ECONOMIC EVENTS FOR INTERPRETABILITY:
   - Economic events are NOT training features
   - They are stored as metadata alongside embeddings
   - Used to answer: "What was the economic environment during this similar
     case?"
   - Provides PMs with richer context for decision-making

8. DEBATE RESOLUTIONS (Key Decision Points):
   - VS Discretization: Continuous embeddings win (preserves precision)
   - VS LSTM: Transformer wins (no forgetting, bidirectional)
   - VS Raw XGBoost: Transformer wins (preserves time order)
   - VS Faiss-only: XGBoost wins for accuracy, Faiss for interpretability
   - VS Keeping all features: Drop redundant, keep structural
   - VS Pre-solving correlations: Let Transformer handle them
   - VS Binary signals: Use raw continuous values
   - VS TTM: Drop it; model learns better relationship
   - VS MACD_L/oSlowK/oSlowD: Drop (redundant)
   - VS BIAS_Diff/Push_Diff: Drop (complex conditional noise)
   - VS SPY_O/SPY_H/SPY_L: Drop (SPY_C sufficient)
   - VS Economic events as features: Use only for interpretability

PART 7: FREQUENTLY ASKED QUESTIONS
================================================================================

Q: "Isn't the encoder looking at the future?"
A: No. It processes ONLY Days 1-252 (the past window). "Bidirectional" means
   left-to-right AND right-to-left WITHIN the historical window, not into
   the future. It never sees Day 253.

Q: "Does the encoder lose information?"
A: Yes, it's lossy compression. But it removes noise and keeps underlying
   signal, compressing 3,000+ raw numbers into 768 meaningful market state
   numbers.

Q: "Why not just use raw flat vectors in XGBoost?"
A: XGBoost loses time order; treats 252 days as independent features.
   Transformer preserves time relationships and learns cross-day patterns.

Q: "Why both Faiss AND XGBoost? Why not just one?"
A: Faiss = Interpretability (show similar cases, gain trust). XGBoost =
   Accuracy (calibrated probability, uses all data). Different tools for
   different goals. They are parallel, NOT a pipeline.

Q: "Why 252 days instead of 60?"
A: Quarterly data needs at least 2-3 updates in the window. 252 days =
   4 quarterly updates (enough to see trends). 60 days = only 1 quarterly
   update (too short).

Q: "Do I need to provide binary crossover signals (SMA_20 crossed SMA_200)?"
A: No. Provide raw SMA_20 and SMA_200. The Transformer learns the gap, slope,
   and acceleration dynamically. Binary signals lose information.

Q: "Should I keep TTM (2*STD - 1.5*ATR)?"
A: No. Delete it. The model will learn a better, adaptive, possibly
   non-linear relationship between STD and ATR. Don't impose fixed
   linear assumptions on the model.

Q: "How do I combine daily, weekly, monthly, and quarterly data?"
A: Forward-fill all slower frequencies to daily. Every day has the same
   number of columns. The Encoder doesn't care about frequencies; it sees
   a fixed vector per day.

Q: "What is the computer requirement?"
A: 32GB RAM is more than enough. Model uses <2GB. Training takes 2-6 hours
   on CPU. GPU not required at this scale.

Q: "Why remove SPY_O, SPY_H, SPY_L but keep SPY_C?"
A: SPY_C (stock close / SPY close) captures the core relationship between
   market and stock. The open, high, and low do not add independent
   information beyond what close provides for this context.

Q: "What are economic events used for if not as features?"
A: Economic events (earnings, GDP, CPI, Fed announcements) are stored as
   metadata alongside embeddings. They are used to provide contextual
   explanation for retrieved similar cases: "This similar case occurred
   during rising CPI and Fed hiking cycle."

Q: "How do you handle each economic release being a separate dataset?"
A: Each release is loaded separately. They are merged together by their
   RELEASE DATE (not period end date). This creates a daily-aligned
   dataset where each day has the most recently released economic data.
