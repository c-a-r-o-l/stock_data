03 · Where Plan 3 breaks

Ranked, worst first

The first two are core-wrong — the plan as written can't be built into something whose results mean anything. The rest are serious but repairable.

F1

The label isn't a function of the input

The label is cross-sectional: top decile among peers on day t. Plan 3's embedding sees one stock's 252-day history and never sees the peers. Two stocks with identical windows can carry opposite labels depending on what the other 312 names did that day — from the model's seat, that's irreducible label noise baked in by the architecture. This is the structural mismatch that locked the cross-sectional (stock, date) spine; Plan 3 still stands on the rejected framing. Every downstream choice in the plan — the per-stock windows, the per-stock time-series z-scores, the absence of any cross-sectional standardization — inherits this.

F2

The central component has no loss function

Nowhere in Plan 3's ~8 pages does it say what the encoder is trained on. That's not a detail; it's the whole design. There are two candidates and both fail as written. (a) Trained on the label (a classification head): the embedding becomes label-shaped, so FAISS "similar regimes" partly means "similar predicted outcome" — the precedents shown to a PM are the model agreeing with itself, and the interpretability claim is circular. (b) Self-supervised masking: forward-fill duplication lets the model copy adjacent identical cells and score perfectly while learning nothing — it needs block or release-boundary masking, which the plan doesn't know it needs.

Gate condition: no written training objective that answers F1 and F2 → the encoder doesn't enter gate 6. This is the single most useful thing to ask the collaborator for.
F3

Validation is one chronological split — and nothing else

No purge or embargo: with a ~126-day label, windows near the 2018|2019 and 2021|2022 boundaries carry test-period outcomes into training. No effective-N: hundreds of thousands of daily windows overlapping 252 days collapse to roughly ~50 independent half-year periods per stock on the usable data — every AUC computed the Plan 3 way is inflated by sample re-use, not signal. No deflated Sharpe, no multiple-testing discipline, and the backtest itself is a checkbox in the open-items list. This is the section where the plan dies in front of anyone who's sat on a desk.

F4

Survivorship silence, aggravated by SYMBOL as a feature

The plan never mentions universe construction, and its 28 features include the ticker. On a survivors-only dataset the cheapest signal available is "this symbol goes up" — the model can memorize the answer key, and the biased universe will reward it in-sample. Entity embeddings are a legitimate technique in general; here, with ~313 fixed survivors and a top-decile label, it's an invitation.

F5

The alpha map is testimony, not evidence

"Close > Trigger > Itrend confirms trend continuation (~100% reliability)" is precisely the kind of claim the entire validation apparatus exists to destroy. The four alpha sources are fine as hypotheses to test — α·3 (regime-gated stock factors) even matches your own working thesis about where the edge lives. As assumptions to build on, they're poison: nothing in the plan tests any of them.

Minor notes — real, but not structural

The label is defined two ways. Part 1 says P(6-month return > 50%); everywhere else says top decile. Those are very different targets — one is absolute, one is relative. The ambiguity is F1 in miniature.

"Time-series z-score" over an unspecified window. If the mean/std are computed over the full series, that's look-ahead. Must be expanding or rolling as-of statistics — the plan doesn't say, which usually means full-sample.

"Forward-fill introduces no bias" is true for causality, false for consequences. The duplication over-weights slow features in any distance metric and sabotages naive masking (F2b). No bias ≠ no cost.

2–6 hours on CPU for a ~40M-parameter encoder over hundreds of thousands of 252-token windows is optimistic by roughly an order of magnitude. Harmless, but it signals the training loop was never budgeted.

04 · Issues with the breakdown itself

Your plan's own exposures

Smaller and fewer, but they exist — and one of them is the kind of gap an interviewer finds in the first ten minutes.

B1

Factor controls are missing entirely

Nowhere in gates 4–7 does the breakdown demand a factor regression of the long-short spread. "Beats buy-and-hold" is not "alpha." A top-minus-bottom decile spread can be fully explained by momentum, size, or value loadings — the claim only survives if the spread's intercept survives a Fama–French-style regression. This belongs in gate 4 (with costs) and again in gate 7 (with the deflated Sharpe).

B2

Its own numbers are stale

"200 stocks, ~2,520 days, ≈500k rows" versus the actual 313 clean symbols and a daily file that spans 1986→2026. Harmless until someone budgets a feature count or an effective-N off the wrong denominator — which is exactly what §02's "low tens of features" advice does.

B3

It declares the horizon decided while it's still open

§03 hard-codes ~126 days; the live decision list still has the exact horizon open. This isn't cosmetic: the purge width, the neighbor admissibility rule, and effective-N all inherit from the horizon. Pin it before the label pipeline exists, or every one of those becomes a parameterized rewrite.

B4

It names survivorship as Necessary but offers no interim path

Gate 1 requires a point-in-time universe. The TradeStation exports cannot satisfy it — they are today's tickers — and CRSP is still pending. The plan should say what's allowed meanwhile: build everything, stamp every result "survivor universe — treat as an upper bound," and design the data layer so CRSP drops in without code changes. Otherwise gate 1 is a wall instead of a gate.

One tension worth writing down

§02 says the statistical budget is "low tens, maybe ~100" features, while the current transformer spec carries ~320 features per token. Both can be right — the 30–50 Vector A shortlist is the binding budget for the core system; the 320 is a gate-6-only concern — but the breakdown never says this explicitly, and it should.

05 · Ground truth — the inventory vs. both plans

How the disk has deviated

Credit first, because it's earned: the ALFRED vintage capture (54 true multi-revision timelines) exceeds what either plan specified · release dates are computed for all 140 series · 313 symbols are aligned across three frequencies · SPY/QQQ benchmarks are carried through every layer · dates are normalized end to end. The macro layer is the strongest part of the pipeline and it follows Plan 3's best idea faithfully.
D1
▮▮▮▮

The universe is survivors-only — now confirmed, not suspected

313 fixed symbols, every file running to 2026, no delisted names anywhere in the tree. Violates the breakdown's gate 1 (Necessary); consistent with Plan 3 only because Plan 3 never looked. Compounded: fundamentals cover 276 of 313, and 30 raw symbols were all-zero and dropped — so fundamental coverage itself correlates with corporate health. Availability bias stacked on survivorship bias.

Interim stance (per B4): proceed, label every result an upper bound, isolate universe membership behind one file so CRSP swaps in cleanly.

D2
▮▮▮▯

Point-in-time macro is approximate before 2016

86 of 140 series use rule-of-thumb release lags across their entire history, and the 54 true-vintage series bunch their pre-2016 vintages at 2016-01-01 — so "what was known then" is partly reconstructed for most of the backtest window. This is a reasonable engineering compromise, but it deviates from the letter of the release-date rule both plans swear by, and it's currently undocumented as a limitation.

Fix: add a lag-buffer switch (+5–10 business days) to 4_merge_macro.py and re-run headline results under it. If the results die under a small buffer, they were leakage wearing a costume.

D3
▮▮▮▯

Cleaning deletes rows; both plans demand a complete daily grid

1_clean_tech.py drops rows on SPY_C=0, OHLC≤0, zero PV counts, and all-zero MACD. If those are warm-up rows at the start of each series, fine. If any are mid-series, the daily calendar has holes: forward returns computed across gaps, misaligned 252-day windows, and different calendars per frequency for the same stock. "Same shape every day" is a rule in both plans; row deletion is the quiet way to break it.

Fix: verify the drops are leading-edge only; if not, switch to keep-and-flag with a validity column.

D4
▮▮▯▯

The locked merge design isn't built — a different one is

The locked decision: per-stock wide parquet, columns suffixed _D/_W/_M/_F, four source date columns, no-lookahead assertions at the join. On disk: per-frequency stacked CSVs (tech_daily.csv is 498 MB), merge_wide.py demoted to "Legacy," and no assertions anywhere. The union step — the exact place forward-fill lookahead happens — hasn't happened, which also means the two flagged issues (bare DATE column, stray unnamed columns) are still open, not resolved.

D5
▮▮▯▯

Gate 1's exit criteria don't exist in src/

The breakdown's bar for advancing past gate 1: a leakage unit test passes, and every factor's constancy/variance is profiled. Neither script exists. The pipeline is at gate 0.9 — a lot of good plumbing, no proof it's watertight.

D6
▮▯▯▯

Headline date ranges oversell the usable window

tech_daily says 1986, monthly says 1970 — but MKT starts 1993, market_merge_daily starts 2000, and parts of the VIX term structure exist later still. The joint window every feature covers is roughly 2000→2026, and effective-N (span ÷ horizon) must be computed on the joint window, not the oldest file. Corollary: Plan 3's 1990–2018 train split is unbuildable with these features.

D7
▮▯▯▯

The universe count drifts by document

~275 in the working spec, 313 in the clean tech set, 276 with fundamentals. Three numbers, no canonical source. Write a universe.csv that names the membership and make every script read it — it's also the seam CRSP slots into later.

06 · What to do next

Seven moves, in order

Write the leakage test and the constancy profile. Closes gate 1's exit bar and, as a side effect, settles D3 — the test will immediately reveal whether row-drops punched holes in the calendar.
Resolve D3 explicitly. Verify the cleaning drops are warm-up-only; otherwise switch to keep-and-flag. Do this before the label pipeline exists, because forward returns are the first thing gaps corrupt.
Build the locked union. Per-stock parquet, _D/_W/_M/_F suffixes, four source date columns, assertions at the join. Retire the ad-hoc merges; resolve the bare-DATE and unnamed-column flags while you're in there.
Freeze universe.csv and write the survivorship caveat into the README now. One file fixes D7 and stakes out the honest framing for D1 before any result exists to oversell.
Add the macro lag-buffer switch to 4_merge_macro.py and make the sensitivity run a standard part of reporting (D2).
Amend the breakdown: factor regression into gates 4 and 7 (B1), pin the label horizon (B3), refresh the stale counts (B2), and state the interim survivorship policy (B4).
For the collaborator: one written page answering two questions — what is the encoder's loss function, and how does a per-stock window predict a peer-relative label. No answers, no gate 6. The 252-day window, the release-date discipline, and the feature audit are theirs and they're keepers; the burden of proof on the rest is also theirs.
