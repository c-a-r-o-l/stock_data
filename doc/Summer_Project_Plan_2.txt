CORE PRINCIPLE: EVERY DAY MUST HAVE THE SAME NUMBER OF FEATURES
================================================================================

Even though your data updates at different frequencies (daily, weekly, monthly,
quarterly), every single day in your 252-day window must have exactly the same
number of columns (e.g., 50 features).

Solution: Forward-Fill (Carry Forward)

- Daily data: Updates every day (changes daily)
- Weekly data: Updates every Friday, carries forward through the week
- Monthly data: Updates on release date, carries forward through the month
- Quarterly data: Updates on release date, carries forward through the quarter
- Static data: Never changes (same value for every day)

WINDOW CREATION
================================================================================

Choose Window Size: 252 trading days (1 year)

Why 252 days?
- Quarterly data updates ~4 times in the window
- Monthly data updates ~12 times in the window
- Weekly data updates ~50 times in the window
- Daily data updates 252 times in the window

This gives the model enough context to learn:
- Daily patterns (short-term momentum)
- Weekly patterns (medium-term trends)
- Monthly patterns (cycle shifts)
- Quarterly patterns (earnings growth, macro regime)

TRAINING THE ENCODER
================================================================================

Training Objective: Contrastive Learning

Goal: Make embeddings of "similar" market states close to each other in the
      768-dimensional space.

Positive Pairs:
  - Two windows that both led to Top 10% returns
  - Two windows that have similar market regimes (e.g., both bull markets)

Negative Pairs:
  - A Top 10% window and a Bottom 10% window
  - A bull market window and a bear market window

Loss Function: Triplet Loss or InfoNCE (Contrastive Loss)

Training Data:
  - 5,000-10,000 windows from 1990-2020
  - Validation: 2020-2022
  - Test: 2023-2024


TWO PARALLEL PATHS
================================================================================

Path A: Vector DB (Faiss)
─────────────────────────

Purpose: Fast similarity retrieval for interpretability

Process:
  1. Encode ALL historical windows into 768-dim embeddings
  2. Store embeddings in Faiss index
  3. On query: Encode today's window → Search Top-50 nearest neighbors
  4. Return: Dates and metadata of the 50 most similar historical states

Output:
  - "NVDA 2023" (same market state)
  - "AVGO 2024" (similar conditions)
  - "META 2013" (comparable environment)

Use: Explainability for PMs ("Why should I trust this prediction?")

Path B: XGBoost Prediction
──────────────────────────

Purpose: Accurate, calibrated probability forecast

Process:
  1. Use ALL historical embeddings (5,000-10,000) as features
  2. Use labels (Top 10% vs not) as targets
  3. Train XGBoost Classifier
  4. On query: Encode today's window → XGBoost predicts probability

Output:
  - P(Top 10%) = 78%

Use: Quantitative decision-making

WHY NO DISCRETIZATION? (CRITICAL DECISION)
================================================================================

Decision: Use Continuous Embeddings (NOT tokenization)

Why:
  1. Financial data is numeric, not categorical
     - RS_90 = 95.4 vs 95.5 → Small difference matters
     - Discretization would treat 89.9 and 90.1 as completely different (loses smoothness)

  2. Preserves exact values
     - EPS = 4.50 → Carried forward exactly
     - GDP = 3.2% → Carried forward exactly

  3. Handles smooth transitions
     - RS_90 moving from 80 to 95 over 60 days → Model sees the slope
     - Discretization would turn this into: MEDIUM → MEDIUM → ... → HIGH (loses the trend)

  4. No arbitrary threshold choices
     - Discretization requires deciding "What is HIGH vs MEDIUM?" (90? 85?)
     - Continuous model learns the optimal threshold automatically

Implementation:
  Linear Projection Layer: (num_factors) → (768)
  This is a learned transformation that preserves all numeric information.


WHY TRANSFORMER ENCODER? (NOT LSTM OR RAW XGBOOST)
================================================================================

| Method           | Time Order? | Long-range? | Bidirectional? | Parallel? |
|──────────────────┼─────────────┼─────────────┼────────────────┼───────────┤
| Raw XGBoost      | ❌ Lost     | ❌ No       | ❌ No          | ✅ Yes    |
| LSTM             | ✅ Yes      | ⚠️ Forgets  | ❌ No (L→R)    | ❌ No     |
| Transformer      | ✅ Yes      | ✅ Perfect  | ✅ Yes (L↔R)   | ✅ Yes    |

Why Transformer wins:
  1. No forgetting: Day 1 and Day 252 can directly interact
  2. Bidirectional: Day 50 sees both Day 1 and Day 252 (better context)
  3. Parallel training: Much faster than LSTM
  4. Attention weights: Interpretable (which days mattered most)

Why NOT raw XGBoost:
  - Loses time order → Treats Day 1 and Day 252 as independent features
  - Cannot learn "trend" or "momentum" patterns

Why NOT LSTM:
  - Forgets Day 1 by the time it reaches Day 252
  - Cannot compare Day 1 and Day 252 directly

  - Captures seasonal patterns (e.g., January effect, summer slowdown)
  - Standard "1-year lookback" in quantitative finance

Note: 252 trading days ≈ 1 calendar year (since there are ~252 trading days/year)

   Algorithm: XGBoost Classifier

DATA LEAKAGE PREVENTION (CRITICAL)
================================================================================

1. Macro Data Alignment (Most Important)
   ─────────────────────────────────────
   ❌ WRONG: GDP Q1 (Jan-Mar) aligned to Jan 1
   ✅ CORRECT: GDP Q1 aligned to RELEASE DATE (end of April)

   Why: The model would be using "future" information to predict the past.
   This makes backtests look amazing but fails in live trading.

2. Forward-Fill Only Uses Past Data
   ─────────────────────────────────
   - Forward-fill means carrying the LAST KNOWN value forward
   - It NEVER uses future values to fill past gaps

3. Train/Validation/Test Split
   ────────────────────────────
   - Train: 1990-2018
   - Validation: 2019-2021
   - Test: 2022-2024
   - NO shuffling (time series must be chronological)

4. No Future Data in Encoder
   ─────────────────────────
   - Encoder only processes Days 1-252 (the past)
   - It NEVER sees Day 253 or future returns
   - Labels are attached AFTER encoding, not used in encoding

FREQUENTLY ASKED QUESTIONS
================================================================================

Q: Why not just use XGBoost on raw data?
A: XGBoost loses time order; treats 252 days as independent features.
   Transformer preserves time relationships and learns cross-day patterns.

Q: Why not use GPT instead of BERT/Encoder?
A: GPT is generative (autoregressive), good for text generation.
   BERT/Encoder is discriminative (bidirectional), good for representation.
   We need representation (embedding for retrieval), not generation.

Q: Why not discretize like in NLP?
A: NLP uses discrete tokens because words have no numeric order.
   Finance has continuous values (95.4, 0.03) where order matters.
   Discretization loses precision and smoothness.

Q: Why both Faiss AND XGBoost? Why not just one?
A: Faiss = Interpretability (show similar cases, gain trust).
   XGBoost = Accuracy (calibrated probability, uses all data).
   Different tools for different goals. Both are parallel, not a pipeline.

Q: Why 252 days instead of 60?
A: Quarterly data needs at least 2-3 updates in the window.
   252 days = 4 quarterly updates (enough to see trends).
   60 days = only 1 quarterly update (too short).

Q: Does the encoder look at the future?
A: No. The encoder only processes the input window (Days 1-252).
   It never sees Day 253 or future returns.
   "Bidirectional" means left-to-right AND right-to-left WITHIN the window.

Q: How do I handle the different frequencies (daily, weekly, monthly, quarterly)?
A: Forward-fill all slower frequencies to daily.
   - Weekly data: Same value for 5 days
   - Monthly data: Same value for 21 days
   - Quarterly data: Same value for ~63 days
   This way, every day has the same number of columns.

Q: Does forward-filling introduce bias?
A: No, because it only uses PAST data to fill future days.
   This is exactly how a real-time system works: you carry the last known value forward.

Q: How do I know if my model is overfitting?
A: 1. Compare train vs validation AUC (should be similar)
   2. Walk-forward backtesting (model retrained periodically)
   3. Out-of-sample testing on 2023-2024 data

SUMMARY
================================================================================

This project builds a Market State Foundation Model that:

1. Takes multi-frequency data (daily, weekly, monthly, quarterly)
2. Aligns everything to a daily calendar via forward-filling
3. Creates 252-day sliding windows (1 year of trading data)
4. Encodes each window into a 768-dim continuous embedding using Transformer
5. Stores embeddings in Faiss for fast similarity search
6. Trains XGBoost on embeddings to predict Top 10% probability
7. Outputs: Probability + Similar historical cases

The key innovation is using a Transformer Encoder with continuous embeddings
to preserve both time order and numeric precision, unlike NLP-style
discretization. This provides both high-accuracy predictions (XGBoost)
and interpretable results (Faiss retrieval).
